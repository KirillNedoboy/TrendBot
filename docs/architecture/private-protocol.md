# Binance USDⓈ-M private protocol catalogue

Status: evidence catalogue and diagnostic matrix for `P04-M02-T001` and `P04-M02-T003`.

Checked: **2026-10-15**. The review used only the current official Binance Developer
Documentation. No Binance API endpoint was called, no credentials were used, and no
order was submitted.

## Scope and evidence rules

The catalogue covers every method currently listed in the USDⓈ-M REST API `Account`,
`Trade`, and `User Data Streams` catalogue sections. The route shown in each row is
the full production REST URL from the published base endpoint. A field is `UNKNOWN`
when the current page did not publish it or it was not independently confirmed during
this review. `NEEDS_VALIDATION` records a contradiction in the same official page.

Every signed endpoint requires the `X-MBX-APIKEY` header, a request signature in the
parameters, and a `timestamp` in milliseconds. `recvWindow` is optional where shown by
the page and its documented maximum is 60000 ms. `TRADE`, `USER_DATA`, and
`USER_STREAM` are Binance security types; this document records the type and does not
implement authentication.

The common error envelope is `{"code": integer, "msg": string}`. The USDⓈ-M General
Info page documents HTTP 4XX for malformed requests, 403 for WAF violations, 408 for
backend timeout, 429 for rate-limit violations, 418 for an IP ban after repeated 429s,
and 5XX for internal errors. A 503 response with `Unknown error, please check your
request or try again later.` leaves execution status **UNKNOWN**; `Service
Unavailable.` is a failed operation to retry later; `Internal error; unable to process
your request. Please try again.` is a failed operation that may be resent; `-1008`
system-level throttling is a failed operation and reduce-only/close-position/cancel
orders are exempt. A 503 unknown result requires reconciliation before a retry. No
numeric project freshness TTL is inferred here.

All endpoint rows below carry the same checked date, `2026-10-15`, and link directly to
the official page that supplied the row.

## Freshness and private execution boundary

`E`, `T`, local receive time, local availability time, and a stable per-session
processing sequence are different causal values. A repeated payload is a duplicate
only when the test fixture's event identity and payload match; equal or late exchange
timestamps do not replace the stable sequence. Algo identifiers are domain data inside
the opaque `o` object and are distinct from event identity. The published text does
not guarantee global uniqueness for them.

The REST documentation says position endpoints should be combined with
`ACCOUNT_UPDATE` for timeliness and accuracy. It also documents that some historical
Algo orders disappear after age/status windows. These facts are evidence constraints,
not authorization. Unknown response status, stale or disconnected user-data state,
expired listen keys, clock skew, authentication/rate errors, or an HTTP 503 unknown
result must remain diagnostic evidence and require reconciliation before any future
execution work. No project numeric freshness TTL is chosen in this catalogue.
